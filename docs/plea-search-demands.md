## Questions for the Team (Assumption Challenges)

### ASSUMPTION_CHALLENGE 1: 「ユーザーは識別子の区切りを知っている」

- **team_assumption:** クエリ `user` で `getUserById` がマッチしないのは「クエリの書き方の問題」
- **user_reality:** 新人や LLM 中心ワークフローのユーザーは「英単語ベース」で考える。コードの命名規約 (camel/snake/kebab) を学習するより、ツールが分解してくれる方が AI 時代らしい
- **evidence_type:** 行動観察 (現実装 `[A-Za-z0-9_-]+` regex)、競合観察 (GitHub の検索は CamelCase を分解する)
- **impact:** 新人離脱率 + LLM 前提の使い方への適合性
- **user_voice:** > 「自分のクエリが悪いのかツールが悪いのか分からない」(田村)

### ASSUMPTION_CHALLENGE 2: 「ctx where と pack --goal は別物だから別実装でいい」

- **team_assumption:** `where` は人間が読むランキング、`pack --goal` は LLM 用 budget 内充填、別レイヤだから別ロジックでよい
- **user_reality:** ユーザー視点では「同じクエリ語で同じ関連度概念」を期待する。違う結果が返ると概念が崩れて両方信用しなくなる
- **evidence_type:** 現実装の分岐 (`crates/ctx-where/...` と `crates/ctx-pack/...` の relevance ロジックが独立している点)
- **impact:** ツール全体の概念モデルの一貫性、README で説明できる範囲
- **user_voice:** > 「`--from-where` で繋いでくれていいし、そもそも同じスコアにしてくれていい」(黒田)

### ASSUMPTION_CHALLENGE 3: 「監査ログは on にできれば説明責任は果たせる」

- **team_assumption:** `[audit].enabled = true` を提供しているのだから規制業界対応は十分
- **user_reality:** 規制業界で求められるのは「記録すること」ではなく「記録の完全性を検証できること」+ 「センシティブな入力をマスクできること」+ 「ログのフォーマットが文書化されていること」の三点セット
- **evidence_type:** README にスキーマも検証コマンドもマスキング設定も書かれていない
- **impact:** Enterprise 採用可否の判断材料が揃わず、競合 (内製 / Sourcegraph Enterprise) に流れる
- **user_voice:** > 「書いてあっても監査人には『証拠』になりません」(沢田)

### ASSUMPTION_CHALLENGE 4 (追加): 「立ち位置は感じ取ってもらえる」

- **team_assumption:** README 冒頭の比較表で repomix / aider と差別化していれば十分、コード検索の文脈で ripgrep と比較するのは "別レイヤ" だから不要
- **user_reality:** 採用判断者は「目の前にあるツール」(rg / ast-grep) との差分でしか新しいツールを評価できない。"別レイヤ" は宣言されない限り認知されない
- **evidence_type:** Pavel のような評論家の典型行動パターン
- **impact:** OSS 認知の広がり、技術ブログ・カンファレンスでの言及
- **user_voice:** > 「立ち位置がぼやけてるツールは紹介できない」(Pavel)
